# PierCast lake-map point feed

## Design

After one coherent surface build passes the existing all-four-lakes and
temperature-integrity gates, the lake-map job extracts the 0–120 hour LMHOFS
surface temperature at all 32 reviewed PierCast cells. The checked-in point
roster is generated from the same `configuredLocation.gridRow/gridColumn`
objects used by `providers/lmhofs.ts`.

- THREDDS builds read the exact flattened LMHOFS regular-grid cell.
- NODD builds use the surface job's one coherent LMHOFS native source and
  interpolate it to that exact reviewed regular-grid coordinate.
- `runs/<surface-run>/piercast-points.json` is immutable and records the NOAA
  cycle, surface run, THREDDS/NODD source, point mapping, valid time, and units.
- `runs/piercast/latest.json` is a 60-second revalidating pointer. It is written
  only after the immutable file and before the surface `latest.json` pointer.
- Any missing city/hour, non-finite value, mapping mismatch, mixed source, or
  pointer mismatch fails closed before publication.

The ingest switch is `PIER_CAST_TEMPERATURE_SOURCE`. Its default and every
value other than the explicit `lake_map` string retain the existing direct
THREDDS path. In `lake_map` mode, each cohort reads the same complete versioned
file through the production map gate. A file, mapping, or delivery failure
falls back to a full direct-THREDDS cohort fetch; the existing fresh archived
cycle remains the final fallback. Sources are never mixed inside a cohort.

`PIER_CAST_MAP_PASS_SECRET` is required only when the switch is `lake_map` and
must be installed as an Edge Function secret. Signed map passes are short-lived
and are never written into samples or logs.

## Validation gate

Do not propose production enablement until at least two NOAA cycles meet all of
these conditions:

1. All 32 cities and 121 hours use the same cycle and source.
2. Each generated point maps to the exact current v63 row/column.
3. Per-city/hour temperature differences from the v63 archive are under
   0.1°F; report mean and maximum differences.
4. Recomputed PierCast scores and bands have no changes. Any difference must be
   explained before enablement.

The validation artifact belongs under `docs/piercast/lake-map-point-validation/`
and is generated by `web/lake-map/job/validate_piercast_points.py` plus
`scripts/validate-piercast-lake-map-scores.ts`.

The initial two-cycle result is checked in at
`docs/piercast/lake-map-point-validation/2026-10-14.md`. It does **not** clear
the production-enable gate: mappings and rating bands match, but isolated
NODD-vs-THREDDS interpolation differences exceed 0.1°F. The switch therefore
remains off and this PR is code/design only.

## Deployment and rollback plan (not authorized by this PR)

1. Before changing `pier-cast-ingest`, download the exact deployed v63 bundle
   into a protected rollback directory using the Supabase function-download
   API/CLI. Record every file and a recursive SHA-256 manifest. Verify the
   downloaded bundle reports deployed version 63 and retain it unchanged.
2. Deploy the reviewed new bundle to staging with
   `PIER_CAST_TEMPERATURE_SOURCE=thredds` (or unset). Confirm the direct path,
   archive commits, and public output are byte/contract compatible with v63.
3. Install `PIER_CAST_MAP_PASS_SECRET` in staging only, set the switch to
   `lake_map`, and observe at least two automatic cycles. Confirm the validation
   gate above, including direct-THREDDS fallback with a deliberately invalid
   staging-only point URL.
4. Present hashes, validation results, and the exact production commands for a
   separate approval. Production starts with the switch OFF. Flip it only after
   a healthy automatic cycle is available in the point feed.
5. Roll back immediately by setting the switch to `thredds`. If code rollback
   is required, redeploy the exact downloaded v63 bytes and verify their
   recursive SHA-256 manifest before restoring traffic. Do not rebuild v63 from
   current `main`; the frozen bytes are the rollback artifact.
